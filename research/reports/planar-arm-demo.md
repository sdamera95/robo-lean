# Planar arm demo: an executable supervisor with a checked refinement

Status, commit `b254787` (the native executable target since commit `d8e99a5`, the Veil differential test since commit `7975d6c`): the executable supervisor, its refinement proofs, the simulation loop and the differential test against Veil below are in the repository. **Verified - formal checking:** the theorems named in the evidence map are checked by Lean's kernel with only `propext`, `Classical.choice` and `Quot.sound`; they concern the formal statements. The compiler and interpreter that run the supervisor, the text protocol, the floating-point simulation and the Python harness are unverified. Nothing here concerns a physical robot.

## What the demo shows

A planar two-link arm (MLS Figure 4.4, printed p. 164) receives target points from a planner. A supervisor admits a requested target only when it lies in the arm's reachable workspace and no command is active, rejects unreachable targets, counts clock ticks while a command is active, and times the command out at a fixed age. The arm follows each admitted target under PD control. Three pieces meet in one loop:

1. **The supervisor runs as Lean code.** `RoboLean.Demo.Supervisor` is a computable timeout supervisor over rational targets (`ℚ × ℚ`), lists, a Boolean flag and a natural-number age, with core imports only. `RoboLean.Demo.Main` wraps it in a line protocol on standard input and output.
2. **Its transitions are proved to refine the design model.** `RoboLean.Demo.SupervisorRefines` proves that the executable guard decides the annulus guard `planarGuard` exactly, that every accepted action is a step of the design relation `Design.PlanarArmTimeoutSupervisor.Step` and every refused one violates a guard of that relation, and that every state reached from the initial state is a reachable design state. The design invariants therefore hold on the executable's states: the age never exceeds the bound, an idle supervisor has age zero, and every commanded target is a position of the ideal arm, reached by the elbow-down inverse kinematics (3.16) of MLS p. 98. The same supervisor is modelled in Veil, where its invariants and a bounded exclusion are checked with SMT reconstruction (see the [Veil report](veil-robotics-verification.md)).
3. **A Python loop simulates the arm and asks the supervisor.** `demo/planar_arm_demo.py` integrates the dynamics (4.10)–(4.11) of MLS pp. 164–165 under the PD law with `K_p = K_v = I`, the gains of the library's stability theorem for this arm, sends every request, admission, rejection, tick, finish and timeout to the Lean executable, and computes each set point from the inverse kinematics in floating point. It writes plots of the end-effector path, the joint angles and the supervisor timeline, and a JSON run log.

The kinematic arm of the workspace certificate points along `+y` at the zero configuration and the dynamic arm along `+x`, as in the book. `RoboLean.Demo.PlanarArmFrames` proves that for every joint vector the two tool positions agree up to the rotation `R_z(π/2)`, so the joint vector that the certificate provides for a target is a set point of the controller for the same target.

## How to run it

Build the library (`lake build`), then from `demo/`:

```sh
uv sync
uv run python planar_arm_demo.py
```

`lake build` also compiles the supervisor to a native executable, the Lake target `planar-arm-supervisor` (`.lake/build/bin/planar-arm-supervisor`). The script starts it with `lake exe planar-arm-supervisor`, run in the top directory of the repository, or runs the command in the environment variable `ROBO_LEAN_SUPERVISOR` instead, for example the interpreter `ROBO_LEAN_SUPERVISOR='lake env lean --run RoboLean/Demo/Main.lean'`, and writes `demo/out/`. On the scripted protocol transcript the native executable and the interpreter give the same thirty-three answers, and on the traces of the Veil differential test below the same 25 666 answers (tests). The supervisor can also be driven by hand, through either command, with one command per line: `params a b bound` (positive rational link lengths written `n`, `n/d` or `n.f`, a natural age bound; resets the state), `request x y`, `admit x y`, `reject x y`, `finish`, `tick`, `timeout`, `state`, `quit`. Each line is answered with `ok <state>`, `blocked <guard>` or `error <reason>`.

The demo's parameters are its own choice; MLS prints none for this arm: `l₁ = 1`, `l₂ = 1/2`, homogeneous bars with `m₁ = m₂ = 1`, mass centres at mid-link, `I_zi = mᵢlᵢ²/12`, horizontal plane (no gravity term, the book's `L = T`), control period 0.5 s, age bound 18 ticks, arrival tolerance 0.02. The scripted scenario has eleven requests: seven inside the annulus `1/2 ≤ r ≤ 3/2` (one exactly on the outer circle), four outside, several arriving while a command is active, and one slow target that times out.

## Veil differential test

The supervisor exists twice as executable code: the Lean executable above, and Veil's executable semantics of the Veil model `PlanarArmTimeoutSupervisor`, the transition system that Veil extracts from the model's actions and explores with `#model_check` and `#simulate`. The two projects run different Lean versions (4.34.1 with Mathlib here, 4.32.0 for Veil) and cannot import each other, so the test joins them through files. `demo/veil_differential_test.py` writes action traces as JSON lines. The Veil file `PlanarArmTimeoutSupervisorReplay.lean`, the model with its state, actions and clauses unchanged, replays each trace from the initial state through the model's generated `enumerableTransitionSystem` (an action is accepted when a transition with its label exists, otherwise the state is unchanged) and writes the state after every action. The script drives the Lean executable with the same traces, under the interpreter and as the native executable, reads the state back with the protocol command `state` after every refused action, and compares acceptance, the pending, commanded, rejected and timed-out targets as sets, the busy flag and the age, action by action. Run it from `demo/` with `uv run python veil_differential_test.py`; it expects the Veil project next to the repository or at the path in the environment variable `ROBO_LEAN_VEIL`.

The traces are 200 random traces of 80 actions over the eleven targets of the scripted scenario at `a = 1`, `b = 1/2` and bound 18 (seed 20261027; ticks are drawn often and finishes rarely, so that commands time out), and the scripted protocol transcript (24 actions on its own six targets, bound 2). On them the three executables agree on all 16 225 states, the 201 initial states and the states after 16 024 actions. Of the actions, 6 584 were accepted, among them 353 admissions, 200 rejections, 3 899 ticks, 156 finishes and 78 timeouts (in 77 traces), and 9 440 were refused; Veil's transition system offered at most one successor for every action and no assertion failure, and the interpreter and the native executable gave identical answers on all 25 666 protocol lines. On the transcript, Veil's states also equal the answers derived by hand from the specification. This is a test on finitely many traces, not a proof that the two semantics agree.

The Veil model also ran on the demo's own instance (`PlanarArmTimeoutSupervisorDemoTable.lean`): the eleven targets with the guard table of the executable at `a = 1`, `b = 1/2`, decided in Lean by kernel reduction and, by `RoboLean.Demo.reachable_eq_true_iff`, the table of `planarGuard 1 (1/2)` on the targets' library points, and bound 18. The instance has `4^11 · (1 + 7 · 19) ≈ 5.6 × 10^8` reachable states, every combination of pending, rejected and timed-out targets with an idle supervisor or one command of each age, which is beyond an exhaustive interpreted search (2.4 × 10^4 to 3.3 × 10^4 states per second measured on smaller searches, falling as they grow; a run stopped after 300 s had not finished). The search to depth 22, which reaches a first timeout, found no violation in 2 899 926 states, and the exhaustive search of the first eight targets of the table found none in all 6 291 456 reachable states, the number the same count gives for eight targets. With SMT trust off, the inductive invariant check, the six non-vacuity traces and the six-action exclusion give the results of the model's own instance; the exclusion is a kernel-checked Veil theorem with only the three standard axioms. These symbolic checks concern every instance.

## Trust boundary

Kernel-checked: the design invariants of the timeout supervisor, the refinement of the executable's transitions and runs to them, the exactness of the executable guard, the reachability of every commanded target by the ideal arm with the elbow-down joint vector, the frame bridge, and the global asymptotic stability of the PD law for the ideal continuous model. Solver-checked with SMT trust off: the Veil model's invariants and traces, two bounded exclusions also kernel-checked in proof-term form. Tested, not proved: the agreement of the Lean executable with Veil's executable semantics of the model on 201 traces, and the absence of violations in the explicit searches of the demo's instance. Unverified: the Lean compiler, the interpreter and the native code generator and linker, Veil's extraction of executable code, the operating system and the subprocess protocol, the floating-point inverse kinematics and integration, the chosen parameters, the behaviour between samples, and the Python harness. A trajectory that lands within tolerance illustrates the loop; it is not evidence for any theorem.
